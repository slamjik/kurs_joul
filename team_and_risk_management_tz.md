# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## «Управление командой и операционными рисками в проекте по созданию комплексной ИС для планирования деятельности кафедры, мониторинга качества обучения и интерактивной визуализации результатов образовательного процесса»

**Наименование системы:** Комплексная информационная система кафедры («КафИС»)  
**Заказчик / Объект автоматизации:** Кафедра гуманитарных и социально-экономических наук (ГиСЭН) Новотроицкого филиала НИТУ МИСИС  
**Срок завершения проекта:** до 25 ноября 2026 г.  
**Критерий успеха проекта:** Разработанное web-приложение, развернутое на внутреннем сервере кафедры и введенное в опытную эксплуатацию со всеми функциональными модулями. Оценка «Отлично» («5») на публичной защите курсового проекта.

---

## 1. ЦЕЛИ И ГРАНИЦЫ ПРОЕКТА

### 1.1. Бизнес-цель и обоснование
- **Проблема:** Документооборот и учебные данные кафедры рассредоточены по разнородным платформам (разрозненные Excel-файлы, локальные папки преподавателей, выгрузки из деканата) и представлены в неструктурированных форматах, что приводит к временным потерям и рискам ошибок при аккредитации.
- **Возможность:** Комплексная оптимизация и автоматизация трудовых процессов заведующего кафедрой, преподавателей и учебно-вспомогательного персонала за счет внедрения централизованной веб-системы.
- **SMART-цель:** Проектирование, разработка, тестирование и ввод в опытную эксплуатацию web-приложения для централизованного хранения учебной документации, контроля нагрузки, мониторинга качества обучения и анкетирования в срок до 25.11.2026.

### 1.2. Границы проекта
- **В границах проекта:**
  - Разработка серверной части (Backend API на Python/Django) и клиентской части (Frontend SPA на React).
  - Модуль планирования педагогической нагрузки с детектированием коллизий по аудиториям, группам и преподавателям в реальном времени.
  - Модуль мониторинга успеваемости с индикацией зоны академического риска ($< 3.0$ баллов) и интеграцией с LMS Moodle через адаптер.
  - Модуль анкетирования удовлетворенности студентов с обеспечением криптографической анонимности.
  - Интерактивный KPI дашборд с аналитическими графиками (Recharts / DataLens).
  - Ролевая модель доступа (RBAC: Заведующий кафедрой, Преподаватель, Администратор).
  - Юридически значимый журнал аудита операций с 30-дневным регламентом хранения.
  - Формирование и экспорт отчетных ведомостей в форматах PDF, Excel, Word.
  - Управление коммуникациями и операционными рисками в команде из 4 человек.
- **Вне границ проекта:**
  - Прямое изменение исходного кода внешней LMS Moodle университета (взаимодействие только через API/адаптеры).
  - Использование внешних сторонних облачных хранилищ данных (в соответствии с регламентом ИБ вуза размещение строго во внутреннем контуре).

## 3. УПРАВЛЕНИЕ КОМАНДОЙ И РЕГЛАМЕНТ ВЗАИМОДЕЙСТВИЯ

### 3.1. Модель коммуникаций
- **Еженедельные координационные встречи (Среда, 45 мин):** Подведение итогов прошедшей недели, разбор блокеров, сверка с календарным планом под руководством Степанова В.О.
- **Встречи с научным руководителем / зав. кафедрой (по контрольным точкам):** Демонстрация промежуточных результатов, фиксация изменений в протоколах.
- **Оперативный канал связи:** Закрытый рабочий чат команды в Telegram для мгновенного решения текущих технических вопросов.
- **Управление задачами и версионирование:** Репозиторий GitHub (`slamjik/kurs_joul`), канбан-доска GitHub Projects, ветвление по модели GitHub Flow (ветки фич $\rightarrow$ Pull Request $\rightarrow$ Code Review $\rightarrow$ слияние в `main`).

### 3.2. Контроль перегрузки команды (*Workload Balancing*)
Для предотвращения риска перегрузки участников команды Степанов В.О. ведет учет загрузки:
- Недельная трудоемкость на одного студента: не более 12–14 академических часов работы над проектом.
- Запрет на постановку параллельных критических задач одному исполнителю.
- Если задача по Backend/QA требует повышенной трудоемкости, аналитик Осадчук И.Д. подключается к верификации тестовых сценариев и подготовке тестовых данных.

## 4. УПРАВЛЕНИЕ ОПЕРАЦИОННЫМИ РИСКАМИ (RISK MANAGEMENT)

### 4.1. Качественная оценка рисков (Вероятность $P \in [1..5]$ × Влияние $I \in [1..5]$)
Ранг риска $R = P \times I$:
- **Низкий (1–6):** Мониторинг в ходе еженедельных созвонов.
- **Средний (8–12):** Обязательное наличие превентивных мер в плане спринта.
- **Высокий / Критический (15–25):** Реализация превентивных мер на архитектурном уровне до начала активного кодинга.

## 5. ТРЕБОВАНИЯ К КОМПЛЕКСНОЙ СИСТЕМЕ

### 5.1. Функциональные требования
1. **Модуль планирования учебной нагрузки:**
   - Учет плановых и фактических часов по преподавателям, дисциплинам, группам и семестрам.
   - Live-валидация пересечений (преподаватель, группа, аудитория, день недели, номер пары).
2. **Модуль успеваемости и мониторинга качества:**
   - Ведение текущих и итоговых оценок (шкала 2.0–5.0).
   - Автоматический расчет среднего балла и выделение студентов зоны риска ($< 3.0$ баллов).
   - Синхронизация с LMS Moodle / импорт ведомостей Excel.
3. **Модуль анонимного анкетирования и рекомендаций:**
   - 5 блоков вопросов: понятность изложения, прозрачность оценивания, актуальность, педагогический такт, условия обучения.
   - Расчет индекса качества ($I_{кач} = 0.5 \cdot Q_{успев} + 0.5 \cdot Q_{удовл}$).
   - Формирование экспертных рекомендаций преподавателю по устранению просадок.
4. **Модуль визуализации KPI:**
   - Интерактивный дашборд с виджетом филиала («73% удовлетворенности»), фильтрацией по кафедрам (ГиСЭН и др.).
   - Графики Recharts (круговая диаграмма качества, столбчатая диаграмма нагрузки, линейный тренд баллов).
5. **Управление доступом (RBAC):**
   - Роли: Заведующий кафедрой (полный просмотр/редактирование, аудит), Преподаватель (только свои часы, оценки и сводный рейтинг), Администратор (управление пользователями, аудит).
6. **Экспорт отчетности:**
   - Выгрузка ведомостей и нагрузки в Excel, генерация официальных протоколов качества в PDF (WeasyPrint) для заседаний кафедры.

### 5.2. Технические требования
- **Стек разработки:** Backend — Python 3.11 / Django 4.2 / DRF; Frontend — React 18 / Vite / Ant Design / Recharts; СУБД — PostgreSQL 15; Кэш — Redis 7.
- **Производительность:** Время отклика API и интерфейса $\le 2$ сек при нагрузке до 50 одновременных пользователей кафедры.
- **Надежность и логирование:** Автоматическая ротация логов Docker (`max-size: 10m, max-file: 3`), автоочистка записей аудита старше 30 дней (`AUDIT_LOG_RETENTION_DAYS = 30`), еженедельный бэкап базы данных.
- **Информационная безопасность:** Шифрование HTTPS, размещение строго во внутреннем контуре вуза (без внешних облаков), запуск бэкенда от непривилегированного пользователя (`appuser:appgroup`, UID 1001), `no-new-privileges:true`.
- **Совместимость:** Корректная работа в браузерах Яндекс Браузер, Google Chrome, Microsoft Edge на разрешениях от 1280×720 до 1920×1080.
